# 1. Seam analysis

**Two stores, one Durable Object, no bridge.** Both file worlds live in the owner's `Person` object, but they are different tables and different APIs.

- The Library lists `PersonFiles` (`packages/agent/src/files/store.ts`): the `files` table in the Person's SQLite, bodies over 16 KiB spilled to R2 under `person/<owner>/files/<path>`. The route is `/app/library` in `packages/agent/src/http/app-routes.ts:151`, which calls `dir.files(person)` and returns the raw listing. The page (`packages/agent/src/http/app/library.ts`) derives a card's kind from the file extension alone (`LIB_KINDS`) and draws a tile, never a thumbnail; `FileEntry.preview` exists in the store but the grid never uses it.
- The agent's working tree is `PersonTree` (`packages/agent/src/tree/tree.ts`), the Agents SDK `Workspace` filesystem in the same SQLite, reached by `Person.treeCall` (`packages/agent/src/objects/person.ts:410`) through `runTreeCall` in `packages/agent/src/tree/rpc.ts`. Nothing lists it to the UI.
- The one file vocabulary (`packages/agent/src/files/tools.ts`) forks on `inTree(path)`: a `work/` path goes to the tree, any other path to `PersonFiles`. So `file_write {path:"work/sudoku-poem.html"}` landed in the Workspace, which `/app/library` never reads. Had the model dropped the `work/` prefix, the file would have shown as an extension-typed "HTML" card with no title, identity or card in chat.

**The missing registration step.** There is no artifact concept anywhere: no table, no slug, no title, no kind beyond extension, no status, no link from a file back to the chat and turn that made it. The only tool that writes a Library item on purpose is `render_document` (`packages/agent/src/render/tools.ts`), and it registers nothing either: it calls `api.save` (which is `Person.documentCall` with `op:"save"`, `packages/agent/src/files/links.ts` `documentCall`) and returns a `SAVED:` line to the model. The step that must exist and does not: after the bytes are saved, write a record (slug, title, kind, path, chat, turn, status) and push an effect that becomes a card.

**The card plumbing exists, for other kinds.** A tool reaches the chat page only through the `EffectBuffer` (`packages/agent/src/chat/tools.ts`). `share_document` is the model: it pushes `{kind:"link", card:{kind:"share", ...}}`; the engine queues it at the barrier (`packages/agent/src/chat/engine.ts:520`), releases it (`engine.ts:572`) through `LinkShelf.show` (`packages/agent/src/chat/links.ts`), which stores it once per card id and frames `{type:"link"}`; the page's `linkCard()` (`packages/agent/src/http/app/chat.ts:283`) draws a `qf-prompt-card` with a title, a line and one "Open" anchor; history replays it from `store.links()` as a `kind:"link"` entry (`packages/agent/src/chat/history.ts`). The `LinkCardKind` union in `packages/agent/src/workspace/surfaces.ts` has no artifact kind, the card has no thumbnail slot, and its `href` is a workshop path or a public share link. An artifact card is a new card kind on this exact path, not a new path.

**Why `render_document` refused on staging.** `documentsNamespace` calls `api.render`, which `packages/agent/src/objects/chat.ts:84` builds as `available(host.render) ? host.render.render(input) : host.render`. The staging host is `singleAccountHost` (`packages/host-cloudflare/src/single-account.ts:41`), where `render` is `unavailable("render", ...)`, so the call returns `HOST_RENDER_UNAVAILABLE` and the tool throws it with "the document was not made and nothing was saved". That is D-0001 behaving. What a host must provide is the `RenderService` contract in `packages/host/src/host.ts:19` (`render(input)` answering a `RenderResult`, plus `toMarkdown`). The only implementation fletch inherited expects pandoc's HTTP server in a container (`RENDER_IMAGE`, port 8080 in `packages/agent/src/render/render.ts`), a Containers binding the self-host `wrangler.jsonc` does not declare and the free plan does not offer. The test host refuses it the same way (`test/support/host.ts:36`), so the hermetic suite already exercises the refusal.

**The staging agent's fallback path.** The operating block (`packages/agent/src/chat/operating-block.ts`) tells the model nothing about artifacts, and the only platform doc on files (`packages/agent/docs/platform/files.md`) describes `file_write` as the way to keep a document. So the model loaded `files` with `tool_search`, called `file_write` to `work/`, an ungated observation for the person's own store, got an honest "saved work/sudoku-poem.html, N bytes", and then framed that as "Made you an artifact". D-0001 held at the tool layer and failed at the product layer: with no artifact verb, the model invented the word.

**The two adjacent chat defects** have specific causes:

- Duplicate completion message. `IDENTITY_LINES[2]` says "Use send_to_user for anything the person should see before you finish; finish with a short plain answer." The model did both with the same content. The live path frames the streamed final text as deltas and the delivered `send_to_user` as a `message` frame (`engine.ts:571`); history draws the assistant text as `m<seq>` and each delivered `send_to_user` as `m<seq>.k`. Two bubbles, two variants, by design of the prompt.
- Raw `***"…"***`. The chat bubble is `el("div", text)` (`chat.ts:154`): plain text, no Markdown at all. The Library already has a safe node-building renderer, `mdRender` and `mdInline` in `library.ts`, which never sets markup. QYVR-188 names this.

# 6. Risks and unknowns

**Platform limits.**
- Durable Object SQLite: a per-object cap of ten gigabytes and a per-value cap of two megabytes; the free plan caps total storage lower. The Person object already holds memory, files under 16 KiB inline, the work tree (the Workspace writes files into the same SQLite) and now records. Artifact bytes over 16 KiB spill to R2, so the row stays small; the risk is the work tree's `TREE_TEXT_MAX` of four mebibytes per file when a builder writes a page there. F5's cap on `artifact_create` content (recommend one mebibyte, the file store's `FILE_MAX`) needs a stated number; a page with inlined images will hit it and should be refused with `ARTIFACT_TOO_LARGE`, not truncated.
- R2 on the free plan: ten gigabytes and a million class A operations a month. Previews add two writes per build. Fine for one owner; measure anyway.
- Rendering and screenshots on Workers: no Chromium runs in a Worker; pandoc needs Containers (paid); Browser Rendering is a binding whose free allowance exists but is small (minutes per day and a concurrency cap) and must be proven on the Q1 throwaway account before D-0012 is accepted. Without it, previews are refused by name and the audit is text-only. Workers AI image models do not help here.
- The builder runs one sub-agent per Chat alarm, under `SUBAGENT_RUN_TOKENS` (120k) and `SUBAGENT_STALL_STEPS`; a long page build may hit the token ceiling and fail honestly. Measure tokens and wall clock per build on Workers AI models before F8 adds a second round.
- Tool-argument size: a whole page in one `artifact_create` argument may truncate on the smaller Workers AI models, surfacing as `TOOL_ARGS_MALFORMED`. F5's ruling names F7's builder as the way out; measure the truncation rate first.

**Security surface of rendered HTML.**
- Today every served file carries `Content-Security-Policy: sandbox; default-src 'none'; style-src 'unsafe-inline'; img-src data:` and `nosniff`, and the viewer frame is `sandbox=""` with `srcdoc`. That is a sound Phase 1 and 2 boundary: model-written HTML, possibly steered by injected page content, cannot run script, reach the network or read the app's cookies. D-0011 should pin this with a planted test so no part loosens it by accident.
- Phase 3 loosens it to `allow-scripts` on an opaque origin. Remaining channels to close: `connect-src` must stay absent (a script could otherwise exfiltrate inlined data to any public endpoint), `allow-popups` and `allow-top-navigation` must never be granted, `referrerpolicy` stays `no-referrer`, and the postMessage bridge must check the frame's identity and the message's shape, treating every message as data. A public share of a scripted page is the same bytes with the same header, so it runs nothing for a stranger.
- Inlined data (F12) is injected into markup: the escaping of `</script>` and `<!--` inside the JSON needs its planted test.
- The builder's write scope (one slug's file) and the audit never executing anything keep the model's authority where it is; `artifact_invoke_action` is an action under the grants engine, so a card asks before the first run.

**What to measure before committing to Phase 3 (D-0013 and F13).**
- From F6 onward on Kyle's preview: artifact count and the Person object's SQLite size after a month; p50 and p95 page size; share of artifacts over the inline cap.
- From F7 and F8: build wall clock and tokens per artifact, the audit's P0 rate and how often two rounds leave something open, and how often the builder is cut off by the ceiling or the stall rule.
- From F9: capture availability on the free account (the spike), capture time, and how often a card shows "No preview on this setup".
- From F12: whether the data-bound pages Kyle actually asks for are views over a job's output (a snapshot the job refreshes) or need writes from the page. If every real case is a snapshot, F13's object is not needed yet and D-0013 should wait.
- A security review of the bridge design before the F13 session, since the loosened sandbox is the one change in this plan that widens what model-written content can do.
